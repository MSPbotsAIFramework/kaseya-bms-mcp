## Requirement understanding

One line: Give the Agent platform service desk, project management, and billing operations against Kaseya BMS.

The ticket is a one-line ask plus a link to the Kaseya BMS plugin page on the connector
marketplace (`conduit.wyre.ai/plugins/kaseya-bms`). It is the "[PSA] Kaseya BMS" leaf under the
`MCP Epic` (PRD-21190): it asks for an MCP connector to Kaseya BMS covering three capability
areas — service desk, project management, billing — not a specific bug or a specific new tool.
The marketplace page (fetched 2026-10-30) repeats the same three words verbatim and adds no
further detail, so the three capability areas are the only requirement signal available; the rest
of this document is read off what Kaseya BMS's own API actually offers for each of them.

## Current state

`MSPbotsAIFramework/kaseya-bms-mcp` already exists (checked via `mbp.py mcplock info`, confirmed
by cloning) — it is not a new-connector ticket. Current `main` (4ca11bf, 2026-10-23) ships 10
tools across five modules (`src/kaseya_bms_mcp/tools/{tickets,time_entries,crm,finance,service}.py`,
registered in `server.py:117-125`):

| Area | Tools (`README.md` Tools table) |
|---|---|
| Service desk | `kaseya_bms_list_tickets`, `kaseya_bms_get_ticket`, `kaseya_bms_create_ticket`, `kaseya_bms_add_ticket_note` |
| Time / billing | `kaseya_bms_list_time_entries` (has a `billable` filter) |
| CRM | `kaseya_bms_list_accounts`, `kaseya_bms_list_contacts` |
| Finance / billing | `kaseya_bms_list_contracts` |
| Service | `kaseya_bms_list_service_catalog`, `kaseya_bms_search_knowledge_base` (stub: BMS has no KB endpoint) |

Checked against the three capability words in the ask:

- **Service desk** — covered (tickets: list/get/create, notes).
- **Billing operations** — covered at MVP depth (billable time entries, contracts/finance). No
  invoicing endpoints exist in the BMS v2 API (confirmed below), so "billing" here means what BMS
  itself exposes: time billability and contracts, which the repo already has.
- **Project management** — **not covered.** No tool, filter, or code path in the repo touches BMS
  Projects. `tools/time_entries.py:14` only notes that a time entry *can* reference a project
  (`"""Time entries (time logs) against tickets and projects."""`), it does not expose any
  project data itself.

So this is not the "nothing to do, already covered" case (`mcp-track.md` 2.6) — one of the three
advertised capability areas has a real gap. It is also not a new-repo case — the repo is the one
and only `kaseya-bms-mcp` in MSPbotsAIFramework. This is the "has a repo, description names a
capability the tool table does not cover" row of `mcp-track.md` 2.1: design the missing piece.

**What Kaseya BMS's own API offers for "project management"** — read directly from BMS's public
OpenAPI document, fetched 2026-10-30 from `https://api.bms.kaseya.com/swagger/v2/swagger.json`
(the same spec `README.md`'s "Delivery notes" section cites as the source of truth for this
repo's rebuild; 349 paths total). The project-prefixed paths:

```
GET  /v2/project/projects/summary            -- paged list, filters: AccountId, StatusIds, StartDateFrom/To, Sort/Exclude
GET  /v2/project/projects/{projectId}        -- one project, full detail incl. budget/hours
GET  /v2/project/projects/lookup             -- name-only typeahead (not used below; summary already filters)
POST /v2/project/statuses/search, GET .../lookup, GET/PUT/DELETE .../{id}, PUT .../{id}/reorder/{order}
                                              -- status *administration* (config CRUD), not project data
POST /v2/project/tasks                       -- despite POST, this is a paged *list* of tasks (filter body), not a create
POST /v2/project/tasks/searchselect          -- task typeahead for pickers
GET  /v2/project/tasks/{taskId}/relateditems -- one task's dependencies + related service-desk tickets
```

**There is no endpoint to create or update a project or a project task.** The only POST/PUT/DELETE
project-prefixed paths are the `statuses` ones, which manage the list of status values available
to use on a project (an admin config action), not project/task content. This is a hard API
limitation, not a design choice: a "create project" or "create task" tool cannot be built against
this API version. Documented as a non-goal below rather than left as an open question, because it
is a verified fact about the vendor API, not something a product decision could change.

## Product design

### Goals / Non-goals

**Goals**

- Close the "project management" gap: add read access to BMS Projects (the project itself, its
  tasks, and a task's dependencies/related tickets) so the connector's actual coverage matches
  the three words in the ask.
- Follow the same shape as every other read tool in this repo: paged lists with `top`/`skip`,
  name-based filters resolved to ids the same way `kaseya_bms_create_ticket` resolves `priority`/
  `status`, and the same `{error:{code,message,retryable}}` envelope on failure.

**Non-goals**

- **Creating or editing a BMS project or project task.** The BMS v2 API has no such endpoint (see
  Current state). If Kaseya adds one later, that is a new ticket.
- **Project budget/resourcing editing, Gantt/scheduling views, or workforce-planner data**
  (`/v2/calendar/workforceplanner/...` exists in the spec but is a different feature — staff
  scheduling, not project tracking — and the ask does not mention it).
- **Re-covering service desk or billing.** Both are already shipped; this ticket only adds the
  missing third area.

### Acceptance criteria

- **AC1** — Given valid BMS credentials and no filters, when the caller invokes
  `kaseya_bms_list_projects`, then it gets up to `top` (default 50, max 200) projects — id, name,
  project number, status name, priority name, start/due date, created date — paged the same way
  as the repo's other list tools (`count`, `total`, `page`, `has_more`, `next_skip`).
- **AC2** — Given `kaseya_bms_list_projects` is called with `account_id` and/or `status_names`
  (comma-separated status names, e.g. `"Active,On Hold"`), when a given status name does not
  match any known BMS project status, then the tool returns an `invalid_argument` error naming
  the known status values (the same pattern `kaseya_bms_create_ticket` already uses for ticket
  status/priority names).
- **AC3** — Given a valid project id, when the caller invokes `kaseya_bms_get_project`, then it
  gets the full project record: id, number, name, description, contract, manager, status,
  priority, start/due/completion dates, planned/used hours, planned/actual budget.
- **AC4** — Given an unknown project id, when the caller invokes `kaseya_bms_get_project`, then it
  gets a `not_found` error envelope (never an uncaught exception).
- **AC5** — Given `kaseya_bms_list_project_tasks` is called filtered by any of `project_id`,
  `account_id`, `task_name`, `unassigned`, `my_projects`, then it gets the matching tasks — id,
  name, project name/color, planned hours, start/end date, account id — paged with `top`/`skip`.
  (BMS's task-list response carries no total record count; see Data & API contract for how
  `has_more` behaves here.)
- **AC6** — Given a valid task id, when the caller invokes `kaseya_bms_get_task_related_items`,
  then it gets that task's title, description, dependencies, and related service-desk tickets.
- **AC7** — Given no vendor credentials are attached to the request (same precondition as every
  existing tool), each of the four new tools returns the existing `not_configured` envelope
  instead of raising.
- **AC8** — `tools/list` on the deployed server includes the four new tool names, and the
  server's `INSTRUCTIONS` text (`server.py:42-55`) mentions how to find projects and project
  tasks, so an agent discovers them the same way it discovers the existing ones.
- **AC9 (regression)** — The existing 10 tools' names, required parameters, and parameter types
  are unchanged: `uv run pytest` (including `tests/test_contract_types.py`, which pins backward
  compatibility) passes with the original 10 tools' test cases intact.

### Open questions

None block implementation. One non-blocking note: the field names and shapes in "Data & API
contract" below are read from BMS's live public Swagger document, not from a vendored fixture or
a response this agent captured against a real BMS tenant (no BMS test account is available in
this environment, and per `mcp-track.md` §2.5/§3 that is not a blocker). The dev leg should do

## Tech design

### Conclusion

Extend `kaseya-bms-mcp` with one new tool module, `tools/projects.py`, adding four read-only
tools (`kaseya_bms_list_projects`, `kaseya_bms_get_project`, `kaseya_bms_list_project_tasks`,
`kaseya_bms_get_task_related_items`) against BMS's existing `/v2/project/...` read endpoints.
No new dependencies, no schema/migration (the service has no database), no change to the
credential/transport layer. Service desk and billing tools are untouched.

### Where the current implementation lives

- `src/kaseya_bms_mcp/server.py:99-125` — `create_mcp_server()` builds the `FastMCP` instance and
  registers each tool module; `INSTRUCTIONS` (`server.py:42-55`) is the usage text an agent reads.
- `src/kaseya_bms_mcp/api_client.py:108-176` — `BmsClient.get`/`.post`/`.request`: per-request
  bearer token, retry/backoff, BMS's `{Success,Error,Result[,TotalRecords]}` envelope unwrapping,
  `BmsError` → `{code,retryable}` classification (`classify_status`, `api_client.py:65-84`).
- `src/kaseya_bms_mcp/tools/_common.py` — shared helpers every tool module uses: `compact` (drop
  `None`/`""`), `paging`/`page` (top/skip ↔ `PageSize`/`PageNumber`, `has_more`/`next_skip`),
  `result` (unwrap `.Result`), `run_tool` (catch `BmsError`/`ValueError`/anything else into the
  error envelope, so a tool body never raises), `READ_ONLY`/`WRITES`/`LOCAL` annotations.
- `src/kaseya_bms_mcp/tools/tickets.py:46-71` — `_by_name` + `_priority_id`/`_status_id`: the
  existing name→id resolution pattern (fetch a `.../lookup`, match `Name` case-insensitively,
  raise `invalid_argument`-shaped `ValueError` listing known values on a miss). This is the
  pattern AC2's status-name resolution reuses.
- `src/kaseya_bms_mcp/tools/{time_entries,finance}.py` — the two existing modules closest in
  shape to the new one: GET-based list tools with `account_id`/`account_name` filters and the
  same `paging`/`page`/`compact` composition.
- `tests/test_tools.py:26-48` (`EXPECTED_TOOLS`, `UPSTREAM_PARAMS`) — the tool-surface snapshot;
  `test_tool_names_are_stable` asserts `set(tools) == set(EXPECTED_TOOLS)` exactly, so adding a
  tool without updating this dict fails CI by design (it is the thing standing in for "was this
  surface change intentional and recorded").
- `tests/contract_types.json` + `tests/test_contract_types.py` — pins parameter *types* of the
  pre-existing 10 tools so an old caller's argument shapes keep validating; it iterates only the
  tools already in its baseline file, so new tools need no entry there for this ticket (a future
  ticket could add one once this version itself needs a compatibility floor).

### Option analysis

**Option A (chosen) — new `tools/projects.py` module, GET/POST against `/v2/project/...`, same
shape as the other five modules.** Matches the repo's existing one-module-per-BMS-functional-area
layout (`tickets`, `time_entries`, `crm`, `finance`, `service`); projects is its own BMS area, not
a sub-concern of time entries or tickets, so it gets its own module the same way contracts got
their own `finance.py` instead of being folded into `crm.py`.

**Option B (rejected) — bolt project fields onto `tickets.py` or `time_entries.py`.** Rejected:
mixes two BMS functional areas in one file, breaks the existing 1:1 module-to-area convention,
and `time_entries.py`'s docstring already flags that time entries merely *reference* a project —
it is not the right place to own project *data*.

**Option C (rejected) — implement full project/task CRUD (create/update/close a project or
task).** Rejected: no such endpoint exists in the BMS v2 API (see Current state); building it
would mean inventing a request shape the vendor does not accept, which is exactly what
`legs/design.md` S5 warns against ("找不到落点就说明...不要编一个看起来合理的路径"). If BMS ships
project-write endpoints later, that is new information and a new ticket.

### Data & API contract

All four tools follow the existing convention: BMS's raw field names/casing pass through
unmodified inside the `Result` the way every existing list/get tool already does (none of the
existing tools rename or reshape individual record fields — `page()`/`result()` only unwrap the
envelope, they do not touch field names), wrapped in the same `run_tool` → JSON-string envelope.

**`kaseya_bms_list_projects`** (`READ_ONLY`) — `GET v2/project/projects/summary`

```
top: int = 50 (1..200)             -> PageSize
skip: int | None                   -> PageNumber (paging() helper, same as every other list tool)
account_id: int | None             -> Filter.AccountId
status_names: str | None           -> resolved via /v2/project/statuses/lookup (_by_name per
                                       comma-separated name, same error shape as create_ticket's
                                       priority/status) -> Filter.StatusIds (comma-joined ids)
start_date_from: str | None (ISO)  -> Filter.StartDateFrom
start_date_to: str | None (ISO)    -> Filter.StartDateTo
```

Response: `page(..., "projects", params)` → `{projects: [...], count, total, page, has_more,
next_skip}`. Each project row (BMS `ProjectsListSummaryOutputDto`): `Id, Name, ProjectNumber,
StatusId, StatusName, PriorityId, PriorityName, StartDate, DueDate, CreatedOn`. `TotalRecords` is
present on this endpoint, so `has_more`/`next_skip` behave exactly like `kaseya_bms_list_tickets`.

**`kaseya_bms_get_project`** (`READ_ONLY`) — `GET v2/project/projects/{projectId}`

```
projectId: str (numeric id, same `_number()` validation TicketId uses)
```

Response: `result(...)` → BMS `ProjectOutputDto`: `Id, ProjectNumber, Name, Description,
ContractId, ContractName, ManagerId, ManagerName, StatusId, StatusName, PriorityId, PriorityName,
StartDate, DueDate, CompletionDate, PlannedHours, UsedHours, PlannedBudget, ActualBudget`. Unknown
id → BMS returns 404 → `BmsError(404, ...)` → `not_found` envelope (same path `kaseya_bms_get_ticket`
already exercises for tickets).

**`kaseya_bms_list_project_tasks`** (`READ_ONLY`) — `POST v2/project/tasks`

This is a **list** endpoint reached over HTTP POST (its request body is a filter object, exactly
like `kaseya_bms_create_ticket` uses POST for a write) — the `READ_ONLY` annotation reflects tool
semantics, not the HTTP verb, which is why this is worth calling out explicitly in the tool's own
docstring and in the code review notes.

```
top: int = 50 (1..200), skip: int | None   -> body.PageSize / body.PageNumber
project_id: int | None                     -> body.Filter.ProjectIds = [project_id] if given
account_id: int | None                     -> body.Filter.AccountIds = [account_id] if given
task_name: str | None                      -> body.Filter.TaskName
unassigned: bool | None                    -> body.Filter.Unassigned (BMS types this as int32;
                                               send 1/0, not true/false, to match TasksListFilterDto)
my_projects: bool | None                   -> body.Filter.MyProjects (same int32 note)
```

Response: BMS `TasksListOutputDtoIEnumerableResponse` has **no `TotalRecords` field** (confirmed
against the OpenAPI schema — only `ProjectsListSummaryOutputDtoIEnumerablePagedResponse` carries
one). `page()` already degrades correctly when `TotalRecords` is absent (`total` comes back `None`,
`has_more` computes `False`), but the tool's docstring must say so explicitly — a full page here
does **not** mean there are no more rows, the caller just has to try the next `skip` to find out.
Each task row (`TasksListOutputDto`): `TaskId, TaskName, TaskDescription, ProjectName,
ProjectColor, PlannedHours, StartDate, EndDate, AccountId`.

**`kaseya_bms_get_task_related_items`** (`READ_ONLY`) — `GET v2/project/tasks/{taskId}/relateditems`

```
taskId: str (numeric id, same pattern as projectId/ticketId)
```

Response: `result(...)` → BMS `TaskRelatedItemsOutputDto`: `Title, Description, Dependencies
(TaskDependencyDto), RelatedTickets (TaskRelatedTicketDto)`. Unknown id → `not_found`, same as
`get_project`.

**Errors**: all four reuse the existing taxonomy unchanged — `not_configured` (no credentials,
`run_tool` short-circuits before calling BMS), `invalid_argument` (bad id format, unknown status
name), `not_found` (BMS 404), `unauthorized` (401/403), `rate_limited` (429, retried first),
`upstream_error` (5xx / network, retried on reads). No new error code is introduced.

### Key flow / sequence

```
agent -> POST /mcp tools/call kaseya_bms_list_projects {account_id, status_names}
server.py middleware -> reads X-Kaseya-BMS-* headers -> BmsCredentials in contextvar
projects.py -> if status_names: GET v2/project/statuses/lookup -> _by_name() each name -> ids
             -> GET v2/project/projects/summary?Filter.AccountId=...&Filter.StatusIds=1,3&PageSize=...
BmsClient.request -> unwrap {Success,Error,Result,TotalRecords} -> page() -> JSON string
run_tool -> logs tool=kaseya_bms_list_projects outcome=ok -> returns to agent
```

`kaseya_bms_get_task_related_items` and `kaseya_bms_get_project` are single-call (no name
resolution step). `kaseya_bms_list_project_tasks` is single-call with a POST body instead of a
query string; no status/name resolution needed since its filters are already id/text-based.

### Non-functional

- **Multi-tenant isolation**: inherited unchanged. Every new tool goes through the same
  `get_client_from_context()` → per-request `contextvars.ContextVar` credentials
  (`server.py:60-66,100-121`) as every existing tool; no new module-level or shared state is
  introduced, so the existing isolation tests (`tests/test_middleware.py`, `tests/test_no_cookies.py`)
  already cover the new tools structurally — they exercise the shared middleware/HTTP client, not
  a per-tool mechanism.
- **Idempotency / concurrency**: all four new tools are reads; `READ_ONLY` annotations, retried on
  429/5xx/timeout the same as every other read (`api_client.py:155`). No write path, so no new
  idempotency concern.
- **Performance**: same page-size cap (`MAX_PAGE_SIZE = 200`) and the same oversized-record
  trimming (`_json.py`, already shipped under PRD-21055/PRD-20663) apply automatically — nothing
  new to add.
- **Security**: credentials still arrive only as per-request headers, never logged, never stored
  (`BmsCredentials.__repr__` already redacts the token; unchanged). No new header is introduced.
- **Observability**: `run_tool`'s `tool=... outcome=... ms=...` log line covers the new tools for
  free, same format as the existing ten.

### Rollout & rollback

Purely additive: four new tool names, zero changes to any existing tool's behavior, contract, or
registration order. No feature flag needed — an MCP client that doesn't know about the new tools
simply doesn't call them; one that does gets them the next time it calls `tools/list`. Rollback is
a plain revert of the merge commit (stateless service, no data migration, no persisted schema).
Deploy path is the repo's existing one: the review leg merges to `main` and calls the INT publish
API (`mcp-track.md` §4.4), which redeploys `main` as-is.

- **Tool-surface snapshot**: `tests/test_tools.py`'s `EXPECTED_TOOLS`/`test_tool_names_are_stable`

- **Manual smoke** (per repo SOP, same as every PR here): local `uv run python -m kaseya_bms_mcp`,

### Risks & dependencies

- **Risk — field-shape drift**: the response shapes above come from a live fetch of BMS's public
  Swagger document (not a fixture vendored in this repo), so a field could theoretically differ by
  the time the dev leg implements this. Mitigation: the dev leg's unit tests should assert on the
  field names listed here (so a real mismatch surfaces as a failing assertion against a canned
  fixture, same as any other unit test would), and the "needs a real vendor account" manual case
  above is the actual cross-check once a tenant is available. Low risk: this is the same document
  `README.md`'s own "Delivery notes" section already treats as authoritative for every other tool
  in this repo.
- **Risk — `has_more` on `list_project_tasks`**: BMS's task-list response carries no total count,
  so `has_more` will always read `false` even when more rows exist. Mitigated by stating this
  explicitly in the tool's docstring (an agent that stops paging on `has_more: false` would
  silently miss rows otherwise) — this is a vendor API limitation, not a bug to fix.

**Technical-design refinement** (does not change any AC, acceptance criterion, or user-visible
behavior — within the dev leg's latitude per `legs/dev.md`/`mcp-track.md`, since only the tech
design, not the product design, changed):

- `kaseya_bms_get_project` / `kaseya_bms_get_task_related_items`'s id validation imports the
  existing `_number()` helper from `tools/tickets.py` rather than duplicating it in
  `tools/projects.py`. The tech design said to reuse "the same `_number()` validation TicketId
  uses"; the Change list only listed `_by_name` as moving to `_common.py`, so `_number` was kept
  where it is and imported across modules instead of being promoted alongside it. Flagged here so
  a reviewer who expected `_number` in `_common.py` too knows this was a deliberate, narrower
  choice, not an oversight — it can be moved to `_common.py` in a follow-up if a third module ever
  needs it (2 modules sharing a private helper does not yet meet the "second consumer" DRY bar the
  design applied to `_by_name`).
- `kaseya_bms_list_projects`'s `status_names` resolution does not filter out inactive statuses
  the way `tickets.py`'s `_status_id` does for the ticket-creation default. The ticket code filters
  because it is picking a *default* status to use; here the caller is naming a specific status to
  *filter by*, and a project could still carry a now-deactivated status value on older records, so
  excluding those names would make a plausible filter resolve as "unknown" for no good reason. Not
  tested under either policy in `test_projects.py` (no test exercises an inactive-status filter
  value) because no AC calls for it; noted here as a readable design decision rather than silently
  diverging from the ticket-status pattern cited in AC2.
